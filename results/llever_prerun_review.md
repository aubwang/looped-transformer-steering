# GO WITH CHANGES

Do not launch production until findings 1–4 are addressed. The operator algebra and analysis indexing are sound; the main blockers are orchestration, budget validation, failure recovery, and overinterpretation of the verdict. No GPU/Modal jobs were launched and no project code was edited.

## Must fix before launch

1. **Critical — normal entrypoints fail before submission.** `huginn_addition/llever_app.py:408–414`: `if name=='pred'` is outside `if path`. With default smoke/train arguments, `upstream` is unbound. With only `--train`, it reuses train metadata and compares its null push hash against the push file. **Change:** nest the pred hash check inside the nonempty-path branch; record both upstream run paths there. Require `--train` for pred and the intended upstream paths for eval explicitly, before reading files. Add CPU tests of argument validation for smoke, train, pred and eval using a mocked worker; the present tests never execute this entrypoint.

2. **High — smoke does not validate production memory/time, and the hard budget is not enforced.** `llever_app.py:297–323, 353–361, 398–399`: smoke has only 20 VJP rows, 16 JVP rows, and 26 forced rows; none exercises chunk 128. The tiny-batch linear extrapolation is not a measured production estimate or a guaranteed upper bound. It overcounts fixed G1/base overhead and pred readout work (smoke has four directions versus ten), while missing production memory pressure. The FD factor two is already included in measured pred time: do not multiply by two again. Restricted row count 2,920 and full count 3,880 are correct. Four 600-second workers permit 40 GPU-minutes, even excluding smoke; recommending C/R restriction is not a 30-minute cap. **Change:** in the authorized smoke, benchmark a few representative steps with 128 rows for VJP, two-pass JVP and forced evaluation, plus base chunk 32 and readout gradients at 80 problems; synchronize CUDA and record peak allocated/reserved memory. Separate setup, fixed G1, per-problem base, readout and per-loop work in projections. Require each projected worker including setup to fit below 540 seconds with margin; reject production if even restricted work exceeds the remaining aggregate budget. Track actual elapsed GPU allocation across stages (and clarify whether smoke is inside the cap), and allocate deadlines from the remaining budget. Do not merely increase the timeout.

   Cost sanity check: core weights are about 373M including the adapter, approximately 29 GFLOP per 39-token row-loop forward. Counting frozen-weight VJP as roughly two forwards gives about 301,440 forward-equivalent row-loops at T=48, or 8.8 PFLOP before bases, G1 and coda/readout; total is roughly 10 PFLOP. Twenty minutes is plausible with sufficiently efficient FP64 GEMMs, but unverified, and T=96 is substantially tighter. Weights occupy about 11 GB; a single batch-128 doubled MLP projection occupies about 654 MB, with several retained intermediates per block across six blocks for VJP. Chunk 128 might fit 40 GB, but a small smoke cannot establish that. GPU loading/allocator/backend behavior remains untested.

3. **High — hard shard failures lose local collection and claimed partial results are usually empty.** `llever_app.py:372–382, 420–435`: an ordinary caught stage error returns failed metadata and is handled correctly by the merger. But `list(worker.starmap(...))` can raise on a container timeout/death before any returned shard is saved locally. `out = run_stage(...)` is assigned only on successful completion, so a deadline inside the stage saves an empty NPZ, not completed chunks. The shared volume `meta.json` is also overwritten by both shards. **Change:** persist each returned shard immediately with exception-aware collection; always write aggregate failed metadata and retain successful shards. Use shard-specific volume metadata only until local aggregation. Checkpoint completed chunks to recover useful partial work, or explicitly describe empty failure artifacts rather than claiming partial NPZ recovery. A 540-second check between operations cannot guarantee finally runs before a 600-second hard kill, especially during load or unguarded readout gradients.

4. **High, scientific interpretation — verdicts overclaim what R1/R2 establish.** `docs/llever_design.md:104–120`; `analyze_llever.py:85–93`: R2 is a reasonable prespecified *Huginn-pattern* criterion (0.90 is meaningfully below 0.978, and a positive paired FULL–IDENTITY interval is sensible), but it is not a test of linear response alone. For J approximately a positive scalar times I, FULL and IDENTITY can both predict perfectly: R2 fails even though linear response is exact. Conversely, an observed matrix equal to 100 times FULL has correlation one and can pass R2 despite incorrect quantitative gain. Failure of R1 establishes no significant advantage, not that G already steers; both families can be ineffective or negative. R1 also does not require L's absolute effect to be positive. **Change before seeing results:** preserve the frozen criteria, but explicitly label the outcome as replication of the specified correlation/relative-efficacy pattern; replace “linear response holds” with “response shape predicted, no demonstrated lever advantage,” and remove the inference that R2 failure establishes model-specific linear response. Report absolute L/G effects, slopes, normalized errors and dose ratios beside the label. If quantitative linear response or positive steering is intended to be a pass requirement, preregister additional gain/error/positive-effect criteria now rather than interpreting correlations as those tests later.

## Optional improvements and qualifications

5. **Medium — endpoint sham drift is not a bound on fixed-base linearization error.** `llever_app.py:150–163, 191–203`; `analyze_llever.py:48–50`; `docs/llever_design.md:120`. Causality makes the perturbation dynamics closed at q, but the unperturbed prefix can still evolve after loop 64. Derivatives freeze that prefix; forced runs evolve it. Small drift at loop 112/160 does not bound drift at loop 64 or the intervening displacement. Given the measured decay, extrapolating 5e-5 at 32 by 0.8^32 predicts roughly 4e-8 at 64, so this is probably benign in float64, not a demonstrated failure. **Recommendation:** report base_drift and sham endpoint displacement, and measure prefix drift too; remove “bounds that error.” A small comparison at a later base state or step-size convergence check can diagnose an ambiguous outcome without changing the primary result.

6. **Medium — provenance checks do not bind the push file to a particular training artifact.** `make_llever_pushes.py:31–32`; `llever_app.py:368–371`; `analyze_llever.py:111–120`. T validation and matching pred/eval push hashes are correct, but `train_code_sha256` identifies code, not training data; it is not validated. The fixed output filename can overwrite a previous push file. **Recommendation:** store train NPZ hash, run ID, model revision and design/config hash in an immutable run-specific push artifact, validate them against the supplied training run, and assert `times[-1] == cfg['T'] == push['T']` plus expected row names/order in analysis. Current generated files satisfy these conventions, but malformed/stale files are not comprehensively rejected.

7. **Low — tests cover verdict branches, not all scientific edge cases.** `llever_local_test.py:83–112, 160–176`. The four synthetic worlds really exercise all four outputs through `analyze`, not only the verdict helper; analytic tests independently check J^1..J^48, adjoints and forced responses. However IDENTITY is identically zero in the synthetic worlds; the nonlinear world is a reversed/rescaled matrix, not dose-dependent nonlinearity. All time slices are identical, m_ref=1 in analysis tests, and the T96 test duplicates the endpoint. **Recommendation:** add nonzero IDENTITY, nonunit m_ref, genuinely different time slices with known reversal fraction, restricted C/R rows, a gain-mismatch world and a linear scalar-J world. Assert predictor numerical values, dose ratios and the distinct T96 endpoint, not just key presence.

8. **Low — keep precision assumptions explicit.** `llever_app.py:108–131, 260–279`. The rotary patch is correct for the inspected pinned architecture, but changes constant positional features relative to obs_app. **Recommendation:** assert LlamaRotaryEmbedding and rope_type='llama3', record the patch as a design amendment, and assert `fc` leading dimension is one when retaining only the last base chunk's frequencies. No need to revert the patch for correctness; retaining float32-computed rotary constants would also be numerically safe for derivatives with respect to x because the constants do not depend on x. The patch improves phase precision, not cancellation in the FD calculation. G1 checks both patched paths, so it cannot independently validate the patch itself.
